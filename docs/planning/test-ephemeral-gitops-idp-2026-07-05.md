# 🔬 Cheap Spike Test: Cilium + CAPD + Talos Integration

**Archived (2026-07-06):** this spike's CAPD+Talos approach was superseded during Phase 0 - see
`ADR-capd-talos-bootstrap-incompatibility-2026-07-06.md` for why CAPD was dropped in favor of
`talosctl cluster create` directly, and `PLAN-ephemeral-gitops-idp-2026-07-05.md`'s Phase 0 status
for how the spike's findings were carried forward.
Kept for the historical record of the original test plan, not as current guidance.

Given your established familiarity with orchestrating Kubernetes, Talos, and Cilium, this test bypasses the Flux, `mise`, and SOPS layers entirely. It isolates the single point of failure: **Will Cilium's eBPF requirements play nicely with Talos nodes running inside CAPD Docker containers on your Ubuntu host?**

**Objective:** Provision a CAPD cluster using Talos, install Cilium (without kube-proxy), and verify L4 routing and pod-to-pod communication.

**Step 1: Setup the Bare Minimum Management Cluster**
Spin up a basic `kind` cluster and install the CAPI CLI (`clusterctl`).

```bash
kind create cluster --name capi-test
# Initialize CAPI with Docker and Talos providers
clusterctl init --core cluster-api --bootstrap talos --control-plane talos --infrastructure docker

```

**Step 2: Apply the CAPD Talos Manifests**
The Docker infrastructure provider ships no `--flavor talos` template (the maintained Sidero template collection covers `aws`/`gcp` only), so `clusterctl generate cluster ... --flavor talos` does not resolve.
Apply the project-maintained template instead.
It defines 1 control plane + 1 worker and disables the stock CNI and kube-proxy via Talos `configPatches` (see Step 4 - this is done in the template, not post-hoc).
Kubernetes is pinned to v1.35.x to stay inside Cilium 1.19's tested matrix.

```bash
kubectl apply -f .config/capi/capd-talos-template.yaml
```

**Step 3: Extract the Talosconfig and Kubeconfig**
Wait for the machines to provision, then grab the access credentials.

```bash
kubectl get talosconfig talos-cilium-test-cp-0 -o jsonpath='{.status.talosConfig}' > talosconfig
kubectl get secret talos-cilium-test-kubeconfig -o jsonpath='{.data.value}' | base64 -d > kubeconfig
export KUBECONFIG=$(pwd)/kubeconfig
export TALOSCONFIG=$(pwd)/talosconfig

```

**Step 4: Install Cilium**
The CNI and `kube-proxy` are already disabled by the `configPatches` in the template from Step 2 - the Talos nodes boot without them, so Cilium can own routing and service load-balancing.
Do NOT `talosctl patch machineconfig` post-hoc: under CAPI the machine config is generated by CABPT from the template, and an out-of-band patch fights reconciliation.
Cilium is pinned to 1.19.5 (a maintained line; 1.15 is end-of-life and supports only Kubernetes 1.26-1.29).

```bash
# Install Cilium via Helm
helm repo add cilium https://helm.cilium.io/
helm install cilium cilium/cilium --version 1.19.5 \
  --namespace kube-system \
  --set kubeProxyReplacement=true \
  --set k8sServiceHost=<cp-ip> \
  --set k8sServicePort=6443 \
  --set ipam.mode=kubernetes

```

> Provider version note: `clusterctl init` currently assembles CAPD core v1.13.x alongside older Talos providers (control-plane v0.5.x / bootstrap v0.6.x on the v1alpha3 CRD contract).
> The template applies cleanly at admission (server-side dry-run passes), but this skew is a plausible reconciliation-time failure point - watch for it as the first gate.

**Step 5: The Verification Gates**
If these three checks pass, the architecture is fully viable for your PRD:

1. **DaemonSet Health:** `kubectl get pods -n kube-system` (Are the Cilium pods `Running` or stuck in `CrashLoopBackOff` due to BPF mount errors in the CAPD container?)
2. **Pod-to-Pod Ping:** Deploy two Nginx pods on different nodes and execute a `curl` between their internal IPs.
3. **L4 Load Balancer Allocation:** Deploy a `LoadBalancer` service. Does Cilium successfully allocate an IP, and is it reachable from your Ubuntu host?

If this test succeeds, we can finalize the PRD and move straight to writing the `mise` tasks and Flux manifests.
