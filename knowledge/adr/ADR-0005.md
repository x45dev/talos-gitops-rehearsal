# ADR-0005 - Layered `controllers`/`configs` Flux Kustomization pattern for CRD-provider components

Authored by brownfield discovery from decision evidence in
`docs/planning/PLAN-ephemeral-gitops-idp-2026-07-05.md` (Phase 3, "cert-manager - built
(2026-07-07)", lines 139-145) and corroborated by `clusters/workload/README.md` (lines
34-42).
No prior standalone document recorded this decision; it is extracted here because it
sets a reusable structural pattern with a discernible rejected alternative (staying
flat) and explicit consequences for future components.

## Status

Accepted (native status, inferred: the plan marks cert-manager "built (2026-07-07)" and
the pattern is stated as the rule to follow "for any future CRD-provider component" -
`docs/planning/PLAN-ephemeral-gitops-idp-2026-07-05.md` line 143 - inference, high
confidence).

## Context

Cilium, the repository's first infrastructure component, is reconciled directly by the
root `flux-system` `Kustomization` (a flat model).
cert-manager could not follow that flat model: its `ClusterIssuer`/`Certificate` custom
resources cannot be applied until the cert-manager CRDs exist and its webhook is
serving - an ordering a single flat `Kustomization` cannot express
(`docs/planning/PLAN-ephemeral-gitops-idp-2026-07-05.md` lines 139-143).

A doubt-driven-development review on 2026-07-07 additionally found that the ordering
guarantee had been mis-attributed in an early comment: the webhook-ordering gate rests
on helm-controller's default resource-wait behavior (`spec.install.disableWait`
defaulting to `false`), not on the Kustomization's `wait: true` alone, which the review
verified against the shipped `helmreleases` CRD rather than assuming
(`docs/planning/PLAN-ephemeral-gitops-idp-2026-07-05.md` lines 145).

## Decision

Split any Flux-managed component whose custom resources depend on that component's own
CRDs/webhook into two layers, each its own Flux `Kustomization` custom resource:

* **`controllers/`** - the namespace, `HelmRepository`, and `HelmRelease` that install
  the CRD-providing chart itself.
* **`configs/`** - the component's own custom resources (for cert-manager: the
  `selfsigned` -> `root-ca` -> `local-ca` `ClusterIssuer`/`Certificate` chain), gated
  behind an explicit `dependsOn` on the `controllers` layer.

The two layers are wired via a `<component>.yaml` file of Flux `Kustomization` CRs
(e.g. `clusters/workload/infrastructure/cert-manager.yaml`) with
`cert-manager-configs` `dependsOn` `cert-manager-controllers`.
`infrastructure/kustomization.yaml` lists only `cert-manager.yaml` (the CRs), not the
`controllers/`/`configs/` subdirectories directly, so nothing is double-reconciled
(`docs/planning/PLAN-ephemeral-gitops-idp-2026-07-05.md` lines 141-143).

Components without CRD-ordering needs (Cilium) stay flat; the mixed model - one
component at root, others behind sub-`Kustomization`s - is accepted as the norm, not a
transitional state (`docs/planning/PLAN-ephemeral-gitops-idp-2026-07-05.md` line 143;
`clusters/workload/README.md` lines 38-42).

## Alternatives considered

1. **Force cert-manager into the existing flat model** (reconcile it directly from the
   root `flux-system` `Kustomization`, like Cilium).
   Rejected: a flat `Kustomization` cannot express the required
   CRDs/webhook-before-custom-resources ordering
   (`docs/planning/PLAN-ephemeral-gitops-idp-2026-07-05.md` lines 141-142).
2. **Retrofit Cilium into the same layered pattern for consistency.**
   Rejected (implicitly, by omission): the plan explicitly leaves Cilium's Phase 2
   adoption wiring untouched, accepting a mixed model rather than churning working
   wiring for uniformity alone
   (`docs/planning/PLAN-ephemeral-gitops-idp-2026-07-05.md` line 143: "Cilium was
   deliberately left untouched (no churn to its Phase 2 adoption wiring)").
3. **Rely on `wait: true` alone as the documented ordering guarantee**, without
   verifying it against the actual helm-controller behavior.
   Rejected after the doubt-driven-development review found the attribution was wrong
   in an early comment (correct behavior, wrong stated reason); corrected to attribute
   the guarantee to helm-controller's default resource-wait instead
   (`docs/planning/PLAN-ephemeral-gitops-idp-2026-07-05.md` line 145).

## Consequences

* Any future CRD-provider component follows the `<component>.yaml` +
  `controllers/`+`configs/` pattern; components without CRD-ordering needs may stay
  flat (`clusters/workload/README.md` lines 41-42).
* The ordering gate is accepted to rest on helm-controller's version-agnostic default
  wait behavior rather than a `spec.healthChecks` entry keyed to the (chart-version-
  dependent) `cert-manager-webhook` Deployment name; the residual post-rollout webhook
  race is absorbed by `retryInterval: 1m`
  (`docs/planning/PLAN-ephemeral-gitops-idp-2026-07-05.md` line 145).
  This is a stated trade-off, not an oversight: do not set `disableWait: true` on a
  CRD-provider `HelmRelease` in this tree without also adding an explicit webhook
  `healthCheck`.
* Dex and Cloudflare Tunnel, added afterward, did not need this pattern and stayed flat
  single-`Kustomization` components
  (`docs/planning/PLAN-ephemeral-gitops-idp-2026-07-05.md` line 149).
