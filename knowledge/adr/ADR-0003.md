# ADR-0003 - Host-native `mise` toolchain instead of a devcontainer for v1

Authored by brownfield discovery from decision evidence in
`docs/planning/PLAN-ephemeral-gitops-idp-2026-07-05.md` (Phase 1, lines 87-94, and
"Decisions" item 2, lines 194-195).
No prior standalone document recorded this decision; it is extracted here because it
has a discernible rejected alternative (a devcontainer) and stated consequences,
meeting the bar in the discovery instruction set section 4 for an ADR.

## Context

The `adr_status: accepted` is the native status, inferred from the plan's
"Status: done (2026-07-06)" marking this decision closed
(`docs/planning/PLAN-ephemeral-gitops-idp-2026-07-05.md` line 89 -
inference, high confidence, since the same conclusion is stated twice independently:
Phase 1 status and the "Decisions" section).

Under the original dual-cluster CAPD architecture, a devcontainer had been under
consideration to manage the Docker-in-Docker (DinD) socket-mount topology that CAPD's
nested provisioning required.
The 2026-07-06 substrate re-frame (ADR-0001) removed CAPD and the management cluster
entirely, so the only remaining Docker requirement became `talosctl`'s provisioner
reaching a single Docker daemon socket - a single socket mount, not the DinD
socket-mount topology that made a devcontainer subtle under CAPD
(`docs/planning/PLAN-ephemeral-gitops-idp-2026-07-05.md` lines 91-93).

Two dangling `.devcontainer`-related task references existed in the mise task files
from the earlier design: `setup:project` (`.config/mise/tasks/setup.toml`) and
`test:devcontainer` (`.config/mise/tasks/test.toml`)
(`docs/planning/PLAN-ephemeral-gitops-idp-2026-07-05.md` lines 94-95).

## Decision

Use a fully `mise`-managed, host-native toolchain for v1; do not author a devcontainer
specification.
The two dangling devcontainer-referencing tasks are removed outright rather than
rewired, since their entire content was the broken reference, both pointed at paths
that never existed, and neither has a replacement need under the host-native model:
`sops:project:generate-keypair` already covers the AGE key bootstrap that
`setup:project` was meant to provide, and there is no devcontainer configuration left
to validate with a BATS test suite
(`docs/planning/PLAN-ephemeral-gitops-idp-2026-07-05.md` lines 91-95).

## Alternatives considered

1. **Keep a devcontainer specification for cross-machine reproducibility.**
   Rejected for v1: the toolchain is already fully `mise`-managed (tool versions
   pinned in `.config/mise/config.toml`'s `[tools]` table), and the only Docker
   dependency left is a single daemon-socket reach, so the devcontainer's
   isolation/reproducibility upside no longer offsets its setup cost
   (`docs/planning/PLAN-ephemeral-gitops-idp-2026-07-05.md` "Decisions" item 2, lines
   194-195).
   The plan records this explicitly as revisit-only-if-needed: "revisit only if a
   concrete cross-machine reproducibility problem shows up later"
   (`docs/planning/PLAN-ephemeral-gitops-idp-2026-07-05.md` line 93).
2. **Rewire the two dangling devcontainer tasks instead of deleting them.**
   Rejected: both tasks' entire content was the broken `.devcontainer` reference with
   no replacement need identified, so rewiring would have preserved dead surface area
   rather than removing it (`docs/planning/PLAN-ephemeral-gitops-idp-2026-07-05.md`
   lines 94-95).

## Consequences

* No `.devcontainer/` directory or configuration exists in this repository for v1
  (confirmed absent at discovery time - inference, high confidence, from the Phase 1
  survey of the repository root).
* `setup:project` and `test:devcontainer` mise tasks were removed; AGE key bootstrap is
  covered by `sops:project:generate-keypair` instead.
* This decision is scoped to v1 and is explicitly revisitable: a concrete cross-machine
  reproducibility problem would be grounds to reopen it
  (`docs/planning/PLAN-ephemeral-gitops-idp-2026-07-05.md` line 93).
* Reopened in part by ADR-0006 (2026-07-18): the "do not author a devcontainer"
  consequence was revisited when the cross-machine reproducibility trigger this ADR
  named actually materialized (a second host running the shared toolchain).
  The host-native-on-the-laptop decision above is unchanged.
