# ADR-0006 - Add a devcontainer for cross-machine dev sessions, reopening ADR-0003

Reopens the decision recorded in ADR-0003 (host-native `mise` toolchain instead
of a devcontainer for v1), invoking the explicit revisit trigger that ADR named.
Accepted 2026-07-18 (recorded machine-readably in `adr_status`).
This supersedes ADR-0003 only on the narrow point of whether a `.devcontainer/`
exists; ADR-0003's substantive decision - that the laptop runs the toolchain
host-native via `mise` - stands unchanged and remains the default for local work.

## Context

ADR-0003 chose a host-native toolchain and declined to author a devcontainer for
v1, but scoped that explicitly as revisit-only: "a concrete cross-machine
reproducibility problem would be grounds to reopen it" (ADR-0003 Consequences;
`docs/planning/PLAN-ephemeral-gitops-idp-2026-07-05.md` line 93).

That problem is now concrete.
A second host exists: a Tailscale-joined VPS, provisioned as code and running the
same shared `devbase` container image the laptop uses, built for private
long-running agent/dev sessions (the `x45dev/bootstrap-workspace` VPS and
cross-host-image work).
Working on this repository from that second host means reproducing its toolchain
there, which is exactly the cross-machine reproducibility need ADR-0003 deferred.
A devcontainer is the mechanism that reproduces the toolchain identically on both
hosts, so the trigger condition is met.

One complication had to be resolved before this was viable.
This repository's workload provisions its cluster with `talosctl cluster create`
using the Docker provisioner, and its Cilium LoadBalancer advertises its address
by ARP on the Docker bridge, assuming the client shares that L2
(`.config/mise/tasks/test-talos-spike.toml`).
A naive devcontainer (bridged network, no Docker access) cannot reach either the
Docker daemon or that bridge, which is the subtlety that made a devcontainer
awkward under the original CAPD design and contributed to ADR-0003.

## Decision

Author a `.devcontainer/` that consumes the shared `devbase` base image, split
into a safe default and an explicit, opt-in cluster capability:

1. A thin project `Dockerfile` that `FROM`s the digest-pinned `devbase` image and
   installs a Docker CLI (`docker-ce-cli`, compose and buildx plugins).
   The base ships no Docker client by design; adding it in a thin per-project
   image is the extension pattern the base's own example devcontainer documents,
   and keeps the Docker dependency with the one consumer that needs it.
   The CLI is inert without a socket, so its presence in the default image is
   harmless.
2. A default `compose.yaml` that is a plain, sandboxed dev container: the project
   and `agent-standards` and the AGE key mounted, running as non-root `dev`, with
   no Docker socket and no host networking.
   This is what runs on the VPS for unattended agent sessions, so it holds no
   path to the host.
   Its `dev` uid 1000 matches the host account (guaranteed by the VPS cloud-init
   uid pin) so bind-mounted files line up.
3. An opt-in `compose.cluster.yaml` overlay, layered explicitly and only on a
   host that actually runs clusters (the laptop):
   `docker compose -f compose.yaml -f compose.cluster.yaml up -d`.
   It adds the host Docker socket (docker-outside-of-docker, so `talosctl` and
   the repo's Docker tasks drive the host daemon and Talos nodes are created as
   siblings on the host), `network_mode: host` (so the container sits on the
   Docker bridge L2 that `talosctl` and Cilium's ARP-advertised LoadBalancer
   assume), and a root entry command that aligns a container group to the
   socket's gid at start, then drops back to `dev` for all real work.

The reason for the split is security, not convenience.
Docker-socket access is equivalent to host root: a container holding the socket
can bind-mount `/` and chroot.
Granting that to a container running Claude Code unattended would give any
compromised or misbehaving process an unrestricted path to host root from
container start.
That risk is acceptable when a human drives a cluster on their own laptop, but
not for the VPS agent host, so socket access is a deliberate opt-in the default
never carries.

Scope: the default devcontainer serves cross-machine dev and agent sessions -
editing, linting, committing, and running `mise` tasks against the same toolchain
on any host.
Running the cluster itself stays a laptop task.
The overlay lets `talosctl cluster create` work where Docker has the resources,
but a 1-control-plane + 2-worker Talos cluster requests roughly 6GB for the node
containers alone (talosctl's docker-provisioner default is ~2GB per node), before
Cilium and the Flux payload, and the current VPS has 4GB - a second, independent
reason the VPS is not a cluster-run host.

## Alternatives considered

1. **Keep host-native only, add nothing (status quo of ADR-0003).**
   Rejected: it leaves the second host with no reproducible way to run this
   repo's toolchain, which is the concrete need ADR-0003 said would reopen the
   question.
2. **Bake the Docker CLI into the shared `devbase` base image.**
   Rejected: it bloats a general base for a single consumer's needs.
   A thin project image that `FROM`s the base isolates the dependency and is the
   sanctioned extension pattern.
3. **Resize the VPS so the full cluster runs there too.**
   Deferred, not rejected: an 8GB host would let the cluster run in the
   devcontainer, but it adds cost for no benefit to the edit-and-agent-session
   use case this host is actually for.
   Revisit if running the cluster on the second host becomes a real need.
4. **Bridged container network with published ports instead of host networking.**
   Rejected: it does not put the container on the Docker bridge L2 that Cilium's
   ARP-advertised LoadBalancer requires, so in-container `kubectl` against a
   LoadBalancer service would fail.
5. **One devcontainer with the Docker socket always mounted.**
   Rejected on security review: it would give every VPS agent session a standing,
   host-root-equivalent path (Docker socket = host root) that it never uses,
   since the cluster does not run on the VPS.
   Splitting the socket into an opt-in overlay keeps that capability off the
   unattended-agent default and only on hosts that actually run clusters.

## Consequences

* A `.devcontainer/` now exists (`Dockerfile`, `compose.yaml`,
  `compose.cluster.yaml`, `devcontainer.json`), reversing the "no `.devcontainer/`
  directory exists for v1" consequence of ADR-0003.
* The laptop's host-native `mise` workflow is unchanged and remains the default;
  the devcontainer is additive, for cross-machine reproducibility.
* The default container carries no Docker socket and no host networking, so a VPS
  agent session running in it has no path to the host beyond its own mounts.
  Cluster capability, and its host-root-equivalent socket access, is only present
  when the `compose.cluster.yaml` overlay is explicitly layered on a cluster-run
  host.
* Validated on the VPS on 2026-07-18. With the cluster overlay: the Docker CLI
  reaches the host daemon, the socket-group alignment works, `talosctl` is present
  and queries the Docker provisioner, and in-container SOPS decryption with the
  mounted AGE key works. The default (socket-free) container: workspace writable,
  SOPS decryption works, `mise install` provisions the toolchain, Claude Code runs.
  A full `talosctl cluster create` was intentionally not run there, per the RAM
  reasoning above.
* Under the overlay, the container runs as root only for the socket-group setup,
  then drops to `dev` for all real work, a deliberate trade to keep the socket gid
  portable across hosts.
