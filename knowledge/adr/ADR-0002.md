# ADR-0002 - Cilium 1.19.x + kubeProxyReplacement breaks host-network DNS on Talos 1.13 (Docker provisioner)

Inducted by brownfield discovery from
`docs/planning/ADR-cilium-1-19-kubeproxyreplacement-talos-host-networking-2026-07-06.md`
(native `status: accepted`, native `version: 1.0.0`, native `date: 2026-07-06`),
preserved here almost as-is per the discovery instruction set section 4.
The original document is untouched; this is a copy proposed for induction, not a move.

## Status

Accepted (native status).
Confirmed live during Phase 0 implementation
(`docs/planning/PLAN-ephemeral-gitops-idp-2026-07-05.md`).

## Context

`docs/planning/PRD.md` Section 4 flagged a known risk before implementation:
cilium/cilium#46010 (a single, closed upstream report) describes Cilium 1.19.x with
`kubeProxyReplacement=true` killing host networking on Talos 1.13 during BPF/veth
initialization, and named the documented trigger/fallback (probe 1.18.x if gate 1 fails
with host-networking-death symptoms).

Phase 0's first clean `talosctl cluster create` + Cilium 1.19.5 run passed gate 1 as
originally defined (all Cilium pods `Running`, all nodes `Ready`) - the symptom does
not show up as a Cilium or node-readiness failure.
It surfaced one step later, in gate 2's test workload: `nginx-test` pods stuck in
`ImagePullBackOff`.
`kubectl describe` showed the container runtime failing to resolve
`registry-1.docker.io` via the node's own embedded resolver (`127.0.0.11:53`, Docker's
per-container DNS), with `i/o timeout` and `server misbehaving`.
This is node-level (host-network) DNS, not pod-network DNS - it happens before any pod
exists, when containerd pulls an image on the node's behalf.

Diagnosis ruled out an environment/DNS-flakiness explanation: a sibling `docker run`
container on the same Docker bridge network, run at the same moment, resolved and
reached the same hostnames over the same resolver with zero failures across three
repeated attempts.
A `hostNetwork: true` debug pod scheduled onto the same affected node reproduced the
identical failure, confirming the break was in that node's host network namespace
specifically, not the Docker bridge/embedded-DNS infrastructure shared by all
containers on it.
`cilium-dbg status --verbose` reported no errors and `Host firewall: Disabled`, so the
control-plane's own health surface did not flag it either - this is exactly why the PRD
called out that `kubectl`/Cilium health checks alone would not catch it.

## Decision

Pin Cilium to **1.18.11** (latest 1.18.x at the time of writing) instead of 1.19.5,
with the same `kubeProxyReplacement=true` configuration otherwise.

Verification method matters here: the first re-test (a `helm uninstall` of 1.19.5
followed by `helm upgrade --install` of 1.18.11 on the *same* nodes) still failed, now
on all three nodes including the control plane, which had shown no problem under
1.19.5.
This is a confound, not evidence against 1.18.11: `helm uninstall` removes Kubernetes
objects but does not reverse eBPF programs, `tc` attachments, or
`iptables`/`nftables` rules a terminated `cilium-agent` process already wrote to the
host - the second install inherited stale datapath state from the first.
Tearing the cluster down fully (`talosctl cluster destroy`) and re-provisioning fresh
nodes before installing 1.18.11 gave a clean read: gates 1-3 passed, and the fix held
across two independent full teardown/re-provision cycles.
**Any future re-test of a Cilium version on this stack must use freshly provisioned
nodes, not an in-place `helm` swap**, or a false negative is likely.

## Alternatives considered

1. **Disable `kubeProxyReplacement` under 1.19.x, use standard kube-proxy instead.**
   Rejected: kube-proxy is exactly what the CNI/kube-proxy-disable Talos config patch
   (`.config/talos/cni-none.patch.yaml`, carried over from the CAPD-era template)
   exists to avoid, and re-introducing it duplicates a component Cilium is meant to own
   end to end. Also unproven to actually avoid the bug, since the upstream report
   specifically implicates the BPF/veth init path, not only the socket-LB replacement
   of kube-proxy.
2. **Stay on 1.19.5 and work around the DNS break with a node-level resolv.conf change
   or a pull-through registry cache.**
   Rejected as the *primary* fix (though a registry cache remains a separate,
   legitimate lever for spin-up time per the plan's Phase 4): masks a host-networking
   bug rather than avoiding it, and does not inspire confidence for a system meant to
   run unattended bootstrap tasks reproducibly.
3. **Investigate and fix the 1.19.5 host-networking break directly.**
   Rejected for v1: the upstream issue is a single closed report with no
   maintainer-confirmed root cause or patch to apply; the PRD's own risk note already
   pre-authorized falling back to 1.18.x rather than debugging further, and 1.18.11 is
   inside the same tested Kubernetes 1.32-1.35 matrix as 1.19, so there is no
   compatibility cost to paying.

## Consequences

* `.config/mise/tasks/test-talos-spike.toml`'s `cilium` task installs `cilium/cilium`
  at `1.18.11`, not `1.19.5`.
  Re-check this pin against the upstream issue tracker before ever bumping to a 1.19.x
  line again.
* Phase 2's Flux-adopted `HelmRelease` for Cilium (per the plan) must pin the same
  `1.18.11` chart version and values as this bootstrap task, per the plan's hard
  adoption-ordering constraint - a divergent first upgrade would restart the CNI
  underneath the controller performing it.
* A related, independent finding from the same session: the Cilium chart does not
  annotate its agent `DaemonSet` with a config-checksum, so a `helm upgrade` that
  changes agent-level flags (e.g. `enable-l2-announcements`, needed for gate 3) updates
  the `ConfigMap` but leaves running agents on stale flags until the `DaemonSet` is
  explicitly rolled.
  The `cilium` task now runs `kubectl rollout restart daemonset/cilium` unconditionally
  after every install/upgrade to cover this; carry the same pattern into the Phase 2
  `HelmRelease` reconciliation story if helm-controller upgrades ever change
  agent-level flags.
